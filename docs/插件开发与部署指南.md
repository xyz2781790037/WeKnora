# WeKnora 插件开发与部署指南

本文面向插件开发者和 WeKnora 系统管理员，适用于第一版外部插件协议 `weknora.plugin.v1`。外部插件是独立进程或容器，不链接 WeKnora 的数据库和 Redis，只通过 gRPC 与 `plugin-runtime` 交换被授权的数据。

## 1. 选择插件类型

一个插件可以声明一种或多种能力类型：

| 类型 | `spec.types` | Go SDK 处理器 | 用途 |
| --- | --- | --- | --- |
| 数据源 | `data_source` | `DataSourceHandler` | 从 GitHub、Confluence、目录等来源同步原始文档 |
| 文档解析器 | `document_parser` | `DocumentParserHandler` | 把原始文件转换为 Markdown 和附件 |
| 联网搜索 | `web_search` | `WebSearchHandler` | 把厂商搜索结果转换为统一结果 |
| 模型供应商 | `model_provider` | `ModelProviderHandler` | 提供模型发现、对话、向量和重排能力 |

四类协议都已接入 WeKnora 的对应注册表和调用链，并用 GitHub 数据源插件演示完整安装与同步。开发数据源插件时，插件只返回原始文件；解析、分块、向量化、索引和删除仍由 WeKnora 完成。

## 2. 从模板开始

优先使用主仓库的 `pluginctl` 生成四类插件骨架：

```bash
go run ./cmd/pluginctl init \
  --type web_search \
  --id io.example.search.demo \
  --name "示例搜索" \
  --output ../weknora-search-demo \
  --sdk-path .
```

`--type` 可选 `data_source`、`document_parser`、`web_search` 和 `model_provider`。命令只写入空目录，并生成 `go.mod`、`main.go`、`plugin.yaml`、`Dockerfile`、中文 `README.md` 和 `.github/workflows/compatibility.yml`。该工作流会在 PR 和主分支推送时执行 `pluginctl compat`。

主仓库的 `sdk/plugin/go/template` 仍保留为最小数据源参考。生成或复制到独立仓库后，至少修改：

1. `plugin.yaml` 中的插件 ID、版本、镜像、连接器类型、配置 Schema 和权限。
2. `main.go` 中的配置校验、资源发现和同步实现。
3. `Dockerfile` 中的模块路径和构建方式。

SDK 尚未单独发布模块版本时，可以让插件仓库与 WeKnora 主仓并列，并在插件的 `go.mod` 中临时使用：

```go
require github.com/Tencent/WeKnora v0.0.0

replace github.com/Tencent/WeKnora => ../WeKnora
```

生产发布应固定到包含对应协议和 SDK 的 WeKnora 版本，不应长期依赖未固定的本地源码。

## 3. 编写 plugin.yaml

```yaml
apiVersion: weknora.io/v1
kind: Plugin
metadata:
  id: io.example.datasource.demo
  name: 示例数据源
  description: 从示例服务同步文档
  version: 0.1.0
spec:
  protocolVersion: 1.0.0
  weknoraVersion: ">=0.2.0"
  image: ghcr.io/example/weknora-demo-plugin:0.1.0
  types: [data_source]
  capabilities: [incremental, deletion_sync, checkpoint_resume]
  connectorType: example_demo
  icon: database
  defaultTimeout: 2m
  config:
    schema:
      $schema: https://json-schema.org/draft/2020-12/schema
      type: object
      additionalProperties: false
      properties:
        endpoint:
          type: string
          title: 服务地址
        token:
          type: string
          title: 访问令牌
      required: [endpoint]
    secretFields: [token]
  permissions:
    network: true
    allowedHosts: [api.example.com]
    dataAccess: [document_content, document_metadata]
  supplyChain:
    publisher: io.example
    sourceRepository: https://github.com/example/weknora-demo-plugin
    imageDigest: sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef
    signature: BASE64_ED25519_SIGNATURE
  resources:
    memoryBytes: 268435456
    nanoCPUs: 500000000
    pidsLimit: 64
    maxConcurrency: 4
    callsPerMinute: 120
```

关键约束：

- `metadata.id` 是全局稳定的反向域名 ID，升级时不能改变。
- `metadata.version`、`protocolVersion` 使用语义化版本。
- 数据源插件必须提供唯一的 `connectorType`，创建的数据源实例使用该类型。
- `config.schema` 用于前端动态生成租户配置表单。
- Schema 第一版支持顶层 `string`、`number`、`integer`、`boolean` 和字符串 `array`，以及 `required`、`enum`、`default`、`minLength`、`minimum`、`maximum`；浏览器提交前和宿主调用插件前都会校验。
- `secretFields` 只能填写 Schema `properties` 中的顶层字段；这些字段进入 WeKnora 现有密钥存储，不会通过普通配置接口回显。
- `allowedHosts` 仅在 `network: true` 时有效。插件只能经运行时代理访问这些域名。
- `defaultTimeout` 是默认单次调用超时，系统管理员安装时可覆盖，上限为一小时。
- 清单中的 `image` 必须和安装时传入的镜像一致，避免清单与实际镜像被替换。
- `supplyChain` 把发布者、源码仓库和不可变镜像摘要绑定到 Ed25519 签名；声明后运行时一定校验，严格模式还会拒绝所有未签名插件。
- `resources` 是单插件申请额度，不能超过 `plugin-runtime` 的全局上限；省略或填写 `0` 时继承全局值。

支持的数据访问声明为：`document_content`、`document_metadata`、`query_text` 和 `conversation`。运行时在调用进入插件容器前强制检查，未声明时返回 `PermissionDenied` 并写入审计事件。类型与最低权限对应如下：

| 调用 | 必须声明的数据访问 |
| --- | --- |
| 文档解析 `Parse` | `document_content`、`document_metadata` |
| 联网搜索 `Search` | `query_text` |
| 模型对话 `Chat` | `conversation` |
| 模型向量/重排 `Embed`、`Rerank` | `query_text`、`document_content` |

数据源插件从外部系统生产文档，不接收 WeKnora 已有正文，因此资源发现和同步只受调用配额限制。只声明实现能力真正需要的数据。

## 4. 启动 SDK 服务

```go
manifest, err := plugin.ParseManifest(manifestYAML)
if err != nil {
    log.Fatal(err)
}

handler := &myDataSource{}
server, err := plugin.NewServer(manifest, plugin.ServerOptions{
    Lifecycle:  handler,
    DataSource: handler,
})
if err != nil {
    log.Fatal(err)
}

err = server.Serve(ctx, ":9000")
```

每个清单声明的类型都必须传入对应处理器。SDK 自动提供协议握手、健康检查、配置 JSON 校验、gRPC 注册和优雅停止。

四类处理器分别通过 `ServerOptions.DataSource`、`DocumentParser`、`WebSearch` 和 `ModelProvider` 注册。插件若需要自定义动态配置校验和健康信息，同时实现 `LifecycleHooks`。

四类插件使用同一套 Schema 语法，但配置保存位置和能力约束不同：

| 类型 | 配置作用域 | 清单附加约束 |
| --- | --- | --- |
| `data_source` | 每个数据源实例 | 必须声明唯一 `connectorType` |
| `document_parser` | 每个租户的解析器设置 | 必须声明至少一个 `file_type:*` 能力，暂不支持密钥字段 |
| `web_search` | 每个联网搜索供应商实例 | 密钥字段仅支持 `api_key` |
| `model_provider` | 每个模型实例 | 能力至少包含 `chat`、`embedding` 或 `rerank`，密钥字段支持 `api_key`、`app_secret` |

可通过 `GET /api/v1/system/admin/plugins/type-specifications` 获取宿主当前采用的类型规范，插件脚手架和管理页都以该规范为准。

## 5. 实现数据源同步

数据源处理器实现：

- `ListResources`：返回仓库、空间、目录等可选资源。无需选择层级时可以只返回一个根资源。
- `ResolveResourceAncestors`：恢复资源选择层级；平铺数据源可返回空。
- `Sync`：遍历远端变化并发送文档、删除和检查点事件。

`Sync` 中常用的发送方法：

```go
err := emitter.EmitDocument(plugin.Document{
    ExternalID:  "stable-source-id",
    Title:       "readme",
    FileName:    "README.md",
    ContentType: "text/markdown",
    Content:     rawBytes,
    SourceURL:   sourceURL,
    UpdatedAt:   updatedAt,
    Metadata:    map[string]string{"path": "README.md"},
})

err = emitter.EmitDelete("deleted-source-id")
err = emitter.Checkpoint(json.RawMessage(`{"version":1,"next":20}`))
```

实现时遵守以下规则：

- `ExternalID` 在同一个数据源实例内必须稳定且唯一，不能使用 WeKnora 内部文档 ID。
- `Content` 是原始文件内容，不在插件中分块、向量化或写知识库。
- 每完成一个可安全恢复的批次就发送完整游标。游标是插件自解释的 JSON，WeKnora 原样保存。
- 只有已完成的工作才能写进检查点；重复处理同一个事件必须安全。
- 远端删除使用与原文档相同的 `ExternalID` 发送删除事件。
- 及时检查 `ctx.Done()`，让超时和停机可以终止网络请求并从最近检查点恢复。
- 不在日志中打印完整配置、令牌或文档敏感内容。

## 6. 其他三类处理器

文档解析器通过 `ParseStream.RecvContent` 流式读取原始内容，再用 `EmitMetadata`、`EmitMarkdown` 和 `EmitAttachment` 返回统一结果，避免必须把大文件整体缓存在内存中。

联网搜索处理器接收查询、语言、条数和分页令牌，返回 `WebSearchOutput`。每条结果使用统一的标题、URL、摘要、来源、发布时间和字符串元数据。

模型供应商处理器实现 `ListModels`、`Chat`、`Embed` 和 `Rerank`。`Chat` 通过 `ChatEmitter` 流式发送增量内容；模型只应声明自身实际支持的能力。当前宿主适配器只转发纯文本消息和基础生成参数，工具调用、多模态消息、推理内容回传和结构化输出会明确拒绝，不能静默降级。

文档解析器用 `file_type:<扩展名>` 能力声明可处理格式，例如 `file_type:pdf`。解析器实例的非密钥参数来自系统解析设置，键名为 `plugin.<插件 ID>.<字段名>`。当前外部解析器不接受 URL 输入，也暂不支持密钥字段。

联网搜索与模型供应商的非密钥 Schema 字段会动态显示在已有设置页面。当前联网搜索只允许把 `api_key` 声明为密钥；模型供应商只允许 `api_key` 和 `app_secret`。这些值沿用 WeKnora 现有加密存储，不写入插件安装记录或运行日志。

## 7. 本地测试与构建

在 WeKnora 主仓中测试 SDK：

```bash
go test ./sdk/plugin/go/...
```

在独立插件仓中测试插件：

```bash
go test ./...
WEKNORA_PLUGIN_LISTEN=:9000 go run .
```

启动后可从 WeKnora 主仓执行协议、健康和配置联检：

```bash
go run ./cmd/pluginctl validate --manifest ../my-plugin/plugin.yaml
go run ./cmd/pluginctl doctor \
  --address 127.0.0.1:9000 \
  --manifest ../my-plugin/plugin.yaml \
  --config ../my-plugin/config.json
```

提交或发布前使用统一兼容性检查。省略 `--address` 时只检查清单、WeKnora
版本范围、协议版本和四类配置契约；提供地址后还会检查运行镜像清单、健康状态、
配置以及实际注册的 gRPC 服务：

```bash
go run ./cmd/pluginctl compat \
  --manifest ../my-plugin/plugin.yaml \
  --weknora-version 0.2.0

go run ./cmd/pluginctl compat \
  --manifest ../my-plugin/plugin.yaml \
  --weknora-version 0.2.0 \
  --address 127.0.0.1:9000 \
  --config ../my-plugin/config.json
```

实时兼容性检查依赖当前 Go SDK 自动注册的 gRPC Reflection；旧镜像需要使用当前
SDK 重新构建后再检查。

`pluginctl init` 生成的 GitHub Actions 工作流会自动运行静态兼容性检查。已有插件仓库可加入等价步骤：

```yaml
- name: 检查插件兼容性
  working-directory: WeKnora
  run: go run ./cmd/pluginctl compat --manifest ../plugin/plugin.yaml --weknora-version 0.2.0
```

由于示例插件开发期使用同级 WeKnora 源码，构建 GitHub 示例镜像时传入命名构建上下文：

```bash
docker buildx build \
  --build-context weknora=../WeKnora \
  -t weknora-github-source-plugin:dev .
```

网络环境无法访问官方 Go 模块代理时，可在构建命令中增加
`--build-arg GOPROXY_ARG=https://goproxy.cn,direct`。

发布镜像时使用不可变版本标签，并让 `plugin.yaml` 的 `metadata.version`、`spec.image` 与镜像标签保持一致。

### 签名镜像

发布者先生成并离线保管 Ed25519 私钥：

```bash
openssl genpkey -algorithm ED25519 -out publisher-ed25519.pem
```

镜像发布后，把注册表返回的 `sha256:<64 位十六进制>` 摘要、发布者 ID 和 HTTPS 源码仓库写入 `spec.supplyChain`，暂时留空 `signature`，再执行：

```bash
go run ./cmd/pluginctl sign \
  --manifest ../my-plugin/plugin.yaml \
  --private-key /secure/path/publisher-ed25519.pem
```

把输出的 `signature` 写回清单。`public_key` 提供给实例管理员，并配置到 `WEKNORA_PLUGIN_TRUSTED_PUBLISHERS_JSON`；私钥不得提交到插件仓库、镜像或 CI 日志。签名覆盖插件 ID、版本、镜像、发布者、源码仓库和摘要，任一字段变化都必须重新签名。

离线联调本机构建镜像时，可只给 `plugin-runtime` 设置
`WEKNORA_PLUGIN_IMAGE_PULL_POLICY=if-not-present`。运行时会先确认清单声明的镜像已存在于本机 Docker，存在时跳过远端拉取；生产环境应保留默认的 `always`。

### 发布到 GitHub 插件市场

第一版插件市场自动发现公开 GitHub 仓库。发布者需要：

1. 给仓库添加 `weknora-plugin` Topic。
2. 在默认分支根目录提交合法的 `plugin.yaml`。
3. 确保 `spec.image` 指向 WeKnora 部署环境能够拉取的公开镜像。

市场只展示通过 SDK 清单校验的仓库；安装时仍会重新下载并校验清单。后端每次最多发现并验证 GitHub Search 可返回的 1000 个仓库，搜索、类型、兼容性、认证来源、排序和分页都基于这份库存完成。验证后的库存缓存 10 分钟，翻页和筛选不会重复请求 GitHub 或重新下载清单；GitHub 暂时不可用时返回最近的库存或页面缓存并标记为过期。市场可匿名访问 GitHub API，生产环境建议配置 `WEKNORA_PLUGIN_MARKET_GITHUB_TOKEN` 提高搜索调用限额。

`WEKNORA_PLUGIN_MARKET_OFFICIAL_OWNERS` 和 `WEKNORA_PLUGIN_MARKET_VERIFIED_OWNERS` 分别配置逗号分隔的官方与认证 GitHub Owner。认证只表示实例管理员维护的发布者名单，不代替镜像签名和代码安全审核。

## 8. 启用运行时并安装

直接运行主仓后端时，在 `.env` 或 `.env.local` 启用插件运行时：

```dotenv
WEKNORA_PLUGIN_RUNTIME_ENABLED=true
```

执行 `make dev-app` 后，开发脚本会自动启动 `plugins` profile，改用宿主地址 `127.0.0.1:${PLUGIN_RUNTIME_PORT:-9092}` 并等待端口就绪。首次启动会生成共享令牌并保存到 `.runtime/plugin-runtime-auth-token`，目录权限为 `0700`、文件权限为 `0600`；后续启动始终复用该文件，所以 WeKnora 重启不会再与运行时失配。

整套服务通过 Compose 部署时，推荐仍在 `.env` 中启用运行时，然后使用启动脚本：

```bash
./scripts/start_all.sh --docker
```

脚本会执行相同的一次性生成逻辑并自动启用 `plugins` profile。若由 Docker Secret、Kubernetes Secret 或其他密钥管理系统托管，则把同一个 Secret 只读挂载到主服务和 `plugin-runtime`，并将两边的 `WEKNORA_PLUGIN_RUNTIME_AUTH_TOKEN_FILE` 设置为各自容器内路径；也可以直接注入 `WEKNORA_PLUGIN_RUNTIME_AUTH_TOKEN`，其优先级高于文件。绕过启动脚本直接执行 `docker compose` 时，必须自行注入上述两者之一，并保证主服务和 `plugin-runtime` 读取同一个值。

系统管理员进入“系统管理 → 插件”，粘贴 `plugin.yaml`，按需设置调用超时，依次执行安装和启用。启用数据源插件后，租户管理员可以在知识库的数据源编辑器中选择清单提供的连接器，配置实例并触发手动或定时同步。

生产环境可配置以下运行时策略：

```dotenv
WEKNORA_PLUGIN_MEMORY_BYTES=536870912
WEKNORA_PLUGIN_NANO_CPUS=1000000000
WEKNORA_PLUGIN_PIDS_LIMIT=128
WEKNORA_PLUGIN_MAX_CONCURRENCY=8
WEKNORA_PLUGIN_CALLS_PER_MINUTE=120
WEKNORA_PLUGIN_REQUIRE_SIGNATURES=true
WEKNORA_PLUGIN_TRUSTED_PUBLISHERS_JSON={"io.example":"BASE64_ED25519_PUBLIC_KEY"}
```

前三项通过 Docker 强制限制容器资源；后两项由运行时按插件 ID 执行并发计数和连续补充的令牌桶。清单只能申请不超过这些值的额度，超限安装会被拒绝，调用超限返回 `ResourceExhausted` 并写入审计事件。

运行时会持久化每个容器实际采用的资源策略指纹。升级到支持该机制的版本后，旧插件容器会在 `plugin-runtime` 首次重启时按原启停状态重建一次；之后仅在全局上限或插件清单额度变化时重建。全局策略收紧后，超出新上限或不再满足签名策略的旧插件会被停止并标记错误，不能通过再次启用绕过。

安装和升级也可填写公开的 HTTPS `plugin.yaml` 地址。宿主限制重定向次数、响应大小，并用 SSRF 策略拒绝私网和回环地址；清单地址与 YAML 文本不能同时提交。

也可以通过系统管理员 JWT 调用：

```text
GET    /api/v1/system/admin/plugins
GET    /api/v1/system/admin/plugins/marketplace
GET    /api/v1/system/admin/plugins/type-specifications
POST   /api/v1/system/admin/plugins/inspect
POST   /api/v1/system/admin/plugins
POST   /api/v1/system/admin/plugins/operations/install
GET    /api/v1/system/admin/plugins/operations/:operation_id
GET    /api/v1/system/admin/plugins/:id
GET    /api/v1/system/admin/plugins/:id/events
GET    /api/v1/system/admin/plugins/:id/history
PUT    /api/v1/system/admin/plugins/:id
POST   /api/v1/system/admin/plugins/:id/operations/upgrade
POST   /api/v1/system/admin/plugins/:id/operations/upgrade-latest
POST   /api/v1/system/admin/plugins/:id/check-update
POST   /api/v1/system/admin/plugins/:id/enable
POST   /api/v1/system/admin/plugins/:id/disable
POST   /api/v1/system/admin/plugins/:id/health
DELETE /api/v1/system/admin/plugins/:id
```

插件中心先调用清单预检接口展示网络、允许域名、数据读取范围、能力和密钥字段。管理员确认后，请求携带完整清单摘要；预检与安装之间若镜像、Schema、权限或兼容范围发生变化，后端拒绝操作并要求重新确认。

插件中心使用异步操作接口安装和升级：启动接口返回操作 ID，随后轮询操作状态。后端按清单获取、清单校验、约束检查、镜像准备、运行时验证和持久化这些真实执行边界更新步骤，不使用前端估算百分比。完成的操作状态在主服务内存中保留一小时，且不保存清单正文或配置密钥。原同步 `POST`/`PUT` 接口继续保留兼容。

详情页的更新记录来自系统审计日志，只展示安装和升级事件中的版本、时间与操作者，不读取或保存 GitHub Release 内容。

安装请求体为：

```json
{
  "manifest_yaml": "完整 plugin.yaml 文本",
  "image": "ghcr.io/example/weknora-demo-plugin:0.1.0",
  "call_timeout_seconds": 120,
  "permissions_confirmed": true,
  "permission_digest": "预检接口返回的摘要"
}
```

按地址安装的请求体为：

```json
{
  "manifest_url": "https://example.com/weknora-plugin/plugin.yaml",
  "call_timeout_seconds": 120,
  "permissions_confirmed": true,
  "permission_digest": "预检接口返回的摘要"
}
```

## 9. 升级与卸载

升级清单必须保持相同插件 ID 和 `connectorType`，新版本必须高于当前版本。通过清单地址安装的插件会保存来源地址，管理员可检查最新版并一键进入升级确认；升级仍需重新确认权限。升级由运行时先启动并验证新容器；运行时替换、能力注册或数据库保存任一步失败时，宿主都会恢复旧镜像和旧能力注册。租户数据源配置和同步游标保存在 WeKnora 中，不随插件容器替换而丢失。

主服务启动后每 30 秒检查已启用外部插件；连续两次失败时尝试停止并重新启动，单次健康探测最多等待 15 秒，自动恢复有 2 分钟冷却时间。连续失败次数、恢复次数、最近恢复时间和诊断信息写入插件记录，管理页显示异常状态，也保留手动健康检查入口。

插件管理页的“运行日志”显示容器、网络代理和能力调用事件，包括方法、结果、错误码和耗时，并可按事件类型、结果和时间筛选。事件由主服务写入现有审计日志，遵循审计保留周期；不记录配置、密钥和原始文档内容。网络拒绝同时保留独立的安全审计动作，便于统一安全查询。

卸载前必须先禁用插件，并删除所有仍引用该 `connectorType` 的数据源实例。内置插件只在统一列表中展示，不能通过外部运行时升级或卸载。

## 10. 沙箱边界

生产容器默认使用只读根文件系统、非 root 用户、移除 Linux capabilities、`no-new-privileges`、逐插件 CPU/内存/PID 限制和仅内存 `/tmp`。插件没有数据库、Redis、宿主目录或 Docker Socket 凭据。

运行时按清单的 `dataAccess` 在 gRPC 代理层限制正文、元数据、查询和对话数据；插件即使实现了对应 RPC，未声明最低权限也收不到请求。镜像启动前，运行时把 Docker 实际摘要与清单比对，并使用实例配置的可信发布者公钥验证签名。

外网请求必须使用运行时注入的标准 HTTP/HTTPS 代理，并匹配清单的域名白名单。代理拒绝未声明域名、私网、回环、链路本地和保留地址，并把拒绝事件写入 WeKnora 审计日志。第一版以 Linux 和 Docker 为生产运行环境，原生进程模式只用于开发调试。

## 11. 常见错误

- `incompatible protocol major versions`：插件和宿主协议主版本不同，升级插件 SDK 或宿主。
- `image must match spec.image`：安装请求镜像与清单不一致。
- `secretFields field ... is not defined`：密钥名未在 Schema 顶层 `properties` 中声明。
- `plugin runtime is disabled`：未设置 `WEKNORA_PLUGIN_RUNTIME_ENABLED=true`，或没有使用 `plugins` profile。
- 健康检查失败：检查容器日志、gRPC 监听端口是否为 `9000`、运行时共享令牌和插件网络。
- 外部 API 请求被拒绝：检查 `permissions.network` 和 `allowedHosts`，不要填写 URL 路径。
- `plugin publisher ... is not trusted`：把发布者的 Ed25519 公钥加入运行时可信发布者映射，并重启运行时。
- `plugin image digest mismatch`：清单摘要不是当前拉取镜像的摘要，重新发布或更新清单并重新签名。
- `ResourceExhausted`：插件达到清单或运行时设置的并发/每分钟调用上限。
- 插件无法卸载：先禁用插件，并移除仍使用其连接器类型的数据源实例。
